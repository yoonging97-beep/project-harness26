# R2 — 목적

## 1. 완료 기준 (한 문장)

> G1~G4 BLOCK 실패가 0건이고, WARN 항목이 모두 사용자에게 보고되었으며, 사용자가 최종 웹앱을 승인하면 실행이 완료된다.

- WARN은 해결하지 않아도 되지만, 최종 승인 전에 반드시 보고한다.

## 2. 무엇이 매번 달라지나 (실행 단위)

| 항목 | 값 |
|---|---|
| 실행 1회의 입력 | 기능 ID 1개 + 업무 요청서 1개 |
| 업무 요청서 위치 | `harness/runs/<실행ID>/request.md` (실행마다 1개, 형식은 R4에서 확정) |
| 기준 문서 | `Docs/prd.md`, `Docs/story-service.md`, `Docs/design.md`. 실행 시점의 최신 확정본을 쓴다. |

### 최신 확정본 판정

확정 여부와 버전 추적을 분리한다. `git commit = 확정`으로 정의하지 않는다.

| 확인 대상 | 수단 | 의미 |
|---|---|---|
| 업무적으로 확정됐는가 | 문서의 `status: confirmed` | 확정 여부 |
| 어느 버전을 썼는가 | 기준 문서별 Git commit hash 기록 | 버전 추적 |
| 기록한 버전과 실제 입력이 같은가 | 기준 문서 uncommitted changes = 0 | 입력 일치 |

- 현재 기준 문서 3개에는 `status` 메타데이터가 없다. 지금 추가하지 않고, R4에서 SSOT 메타데이터 규칙과 함께 확정한다. R2-3은 목표 상태로 정의해 둔다.

## 3. 사용자와 역할

| 역할 | 담당 |
|---|---|
| 사용자 | 기획자 1명 (본인) |
| B0 요구사항·정책 담당자 | 사용자 |
| 디자인 실행 | 에이전트 |
| 개발 실행 | 에이전트 |
| 사람의 필수 개입 지점 | R3/R5에서 확정한다 (B0~B4 경계별로 판단) |

## 4. 규칙 (스크립트가 셀 수 있는 형태)

| ID | 규칙 | 판정 |
|---|---|---|
| R2-1 | 기능 ID가 정확히 1개여야 실행을 시작한다. | 기능 ID 수 = 1 |
| R2-2 | 업무 요청서가 정확히 1개여야 실행을 시작한다. | `harness/runs/<실행ID>/request.md` 수 = 1 |
| R2-3 | 기준 문서는 `status: confirmed`인 파일만 사용한다. 실행 시작 시 기준 문서별 Git commit hash를 기록하며, 커밋되지 않은 변경이 있는 기준 문서는 입력으로 사용할 수 없다. | confirmed 기준 문서 수 = 3 AND commit hash 기록 수 = 3 AND 기준 문서 uncommitted changes 수 = 0 |
| R2-4 | 완료하려면 BLOCK 실패가 0건이어야 한다. | G1~G4 BLOCK 실패 수 = 0 |
| R2-5 | 완료하려면 WARN이 모두 보고되어야 한다. | 미보고 WARN 수 = 0 |
| R2-6 | 완료하려면 사용자 최종 승인이 있어야 한다. | 최종 승인 기록 수 = 1 |
